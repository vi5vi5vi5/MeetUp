# config/

**Настройки сервера и правила журнала.** Самый нижний слой: не зависит ни от
чего внутри проекта, и от него зависят все остальные.

```
main.cpp  ──читает──►  config/  ──передаёт──►  network/ · services/ · core/
```

Здесь два файла и две разные задачи.

## ServerConfig — что человек разрешил этому серверу

`meetup.conf` лежит **в папке данных** (`mount/`), рядом с базой. Это не
случайность: `mount/` — примонтированный том, он переживает и пересборку
образа, и `git pull`. Если бы настройки жили в `docker-compose.yml`, менять их
значило бы править файл из репозитория, который затрёт следующее обновление.

Сервер создаёт файл сам при первом запуске — со всеми ключами,
закомментированными и с объяснениями. Раскомментировал строку — значение
поменялось; не тронул — работает умолчание. Поэтому файл заодно и справочник:
какие ключи вообще есть, видно, не заглядывая в README.

Любой ключ переопределяется переменной окружения `MEETUP_<СЕКЦИЯ>_<КЛЮЧ>`
(`MEETUP_WEB_ENABLED=false`) — для тех, кто держит всё в compose и не хочет
лазить внутрь тома. **Окружение сильнее файла.**

### Два решения, которые стоит знать заранее

**Разбор свой, не QSettings.** QSettings считает значение с запятыми списком:
имя сервера «Дача, второй этаж» превратилось бы в пустую строку. Плюс он умеет
переписать файл и растерять комментарии, ради которых файл и заводится.
Свой разбор — полсотни строк и никаких сюрпризов.

**Сломанный конфиг не мешает старту.** Непонятый ключ или значение — это
`warnings` и работа на умолчаниях, а не отказ подняться. Сервер, не
включившийся из-за опечатки в настройке, хуже сервера с настройками по
умолчанию. Но молчать о таком нельзя: все жалобы печатаются на старте, даже
когда журнал выключен, — настройка, которая молча не применилась, хуже
настройки, которой нет.

### Умолчания = вчерашнее поведение

Правило для всех новых ключей: после `git pull` сервер ведёт себя ровно как
раньше, пока в конфиг не полезли руками. Единственное исключение —
`log.level`, и оно сознательное (см. ниже).

## Log — что попадает в журнал

Три уровня:

| Уровень | Что печатается |
|---|---|
| `off` | ничего, включая ошибки |
| `errors` | строки старта, предупреждения и ошибки — **умолчание** |
| `normal` | плюс события: подключения, вход в комнату, регистрации |

Почему умолчание не `normal`: корневой README обещает, что сервер не ведёт
журнала подключений, а сервер печатал в stdout имена участников и коды комнат —
в докере это оседает в `docker logs` навсегда.

Почему не `off`: не поднявшийся контейнер молчал бы, и человеку нечем себе
помочь.

**Как это работает в коде.** Обработчик сообщений Qt делит всё по одному
правилу: `qWarning`/`qCritical` — это «что-то сломалось», печатается всегда;
обычные `qInfo`/`qDebug` — это «что-то произошло», и именно в них попадают имена
и коды, поэтому они печатаются только на `normal`. Переписывать существующие
вызовы не пришлось — они и так стояли правильно.

Исключение одно: категория **`lcApp`** (`qCInfo(lcApp)`). Это строки старта —
версия, порты, какой конфиг прочитан. Личного в них нет, и печатаются они уже
на `errors`. Если добавляете сообщение о жизни сервера, а не о людях, — берите
`lcApp`.

`Log::keepsNames()` отвечает на вопрос «а вы записываете, кто к вам ходит»;
сервер честно отдаёт это в `GET /api/config`, и клиент показывает человеку.

## Версия сборки

`ServerConfig::buildCommit()` / `buildModified()` / `buildTime()` — это не
настройки, а свойства бинаря: они приходят из `-D` на этапе компиляции
(см. `../CMakeLists.txt`), а значения считает хост в `tools/update.sh`. Внутри
образа гита нет и быть не должно — `.git` в контекст сборки не попадает.

**Чем это не является.** Значения сервер сообщает о себе сам. Тот, кто правил
код, правит и эту строку; проверку выполняет тот самый бинарь, который
проверяют. Технической защиты тут быть не может в принципе. Годится как
диагностика («у вас сборка трёхмесячной давности»), не годится как гарантия — и
подписывать это в интерфейсе надо соответственно: «сервер сообщает о себе», а
не «проверено».

## Что уже настраивается

| Ключ | Умолчание | Смысл |
|---|---|---|
| `server.name` | `MeetUp` | Имя инстанса на входе и в десктопе |
| `server.public_url` | — | Внешний адрес для ссылок-приглашений |
| `web.enabled` | `true` | Раздавать ли веб-клиент |
| `auth.registration` | `open` | `open` / `closed` |
| `auth.allow_anonymous_join` | `true` | Пускать ли в комнаты без аккаунта |
| `auth.session_ttl_days` | `30` | Срок жизни сессии |
| `auth.min_password_len` | `8` | Нижняя граница пароля |
| `auth.pbkdf2_iters` | `64000` | Стоимость хеша пароля |
| `rooms.anonymous_create` | `open` | `open` / `account` / `off` |
| `rooms.max_total` | `0` | Потолок разовых комнат (0 — без) |
| `rooms.idle_ttl_s` | `600` | Сколько пустая комната ждёт сборщика |
| `rooms.max_personal_per_user` | `1` | Личных комнат на человека |
| `rooms.code_min_len` | `3` | Нижняя граница кода личной комнаты |
| `rooms.max_aliases_per_room` | `5` | Ссылок-приглашений на комнату |
| `media.max_screen_shares` | `1` | Демонстраций в комнате одновременно |
| `chat.history_size` | `500` | Сообщений в истории комнаты |
| `chat.history_images` | `24` | Картинок в истории |
| `chat.image_max_kb` | `440` | Потолок картинки в чате |
| `log.level` | `errors` | `off` / `errors` / `normal` |

Поднять `max_personal_per_user` выше единицы можно только после миграции
схемы: в старой базе стоял `UNIQUE` на владельца. Сервер снимает его сам при
первом запуске новой версии — см. `SqliteDb::migrate`. Если миграция не
удалась, сервер не поднимется: база при этом цела (всё шло в транзакции), но
работать с ней как с новой нельзя.

Потолок разовых комнат намеренно **не распространяется на личные**: их число и
так ограничено числом аккаунтов, а запереть владельца снаружи из-за того, что
кто-то со стороны наплодил разовых, — худшее из возможных поведений.

## Кто что получает

Слои ниже сети конфига не знают. `AuthService` и `PersonalRoomService` получают
готовые числа (`AuthLimits`, `RoomLimits`), `ConferenceRoom` — `ChatLimits`:
правила не должны зависеть от того, из какого файла взялись настройки. Перевод
«настройка → предел» делает `main.cpp`.

Сетевому слою (`HttpApi`, `ConferenceServer`) `ServerConfig` передаётся целиком:
именно он решает, кого пускать и что отвечать, и именно он отдаёт портрет
сервера наружу.

## Как добавить ключ

1. Поле со значением по умолчанию в `ServerConfig.h` — в свою секцию.
2. Строка чтения в `ServerConfig::load`.
3. Закомментированная строка с объяснением в `kSample` (`ServerConfig.cpp`).
4. Если ключ виден клиенту — добавить в `GET /api/config`
   (`../network/HttpApi.cpp`) и в `../docs/desktop-client-guide.md`.
