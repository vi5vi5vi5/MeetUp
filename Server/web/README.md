# web/

Веб-клиент MeetUp (дизайн «Prism Minimal», React + JSX). Отдаётся встроенным
`HttpFileServer`; точка входа `/` — это `login.html`.

## Сборка

Исходники в этой папке рассчитаны на то, что их можно открыть и сразу
править: JSX в них компилирует `assets/babel.js` прямо в браузере, React —
dev-сборка с проверками разметки. Для разработки это удобно, для посетителя —
нет: получалось 4,4 МБ на каждый заход, и телефон компилировал JSX заново
каждый раз.

Поэтому в эфир уходит не эта папка, а собранная:

```bash
node tools/build.js            # web/ -> web/dist
node tools/build.js --watch    # то же, но пересобирает при правке
```

Сборщику нужен только node — ни `npm install`, ни сети: он вызывает тот же
самый `assets/babel.js`, который лежит рядом. При развёртывании этот шаг
делает `docker build` (в стадии сборки образа стоит `nodejs`), поэтому у того,
кто поднимает свой сервер, из инструментов по-прежнему только docker.

Что меняется в `dist` по сравнению с исходниками:

- блок `<script type="text/babel">` со страницы скомпилирован в
  `assets/pages/<страница>.js`, а сам `babel.js` в раздачу не попадает;
- React подменён на production-сборки (`react.production.min.js`,
  `react-dom.production.min.js`);
- к каждой ссылке на `assets/…` приписан `?v=<хэш содержимого>` — версию
  больше не нужно поднимать руками, а забытая правка не уедет в чужой кэш на
  сутки (`Cache-Control: public, max-age=86400`);
- итог: **4467 КБ → 351 КБ**, а по сети с gzip (включён в `proxy/nginx.conf`)
  — около **98 КБ** на страницу конференции.

`web/dist` в git не хранится: в репозитории лежит исходник, а не результат.

## Стенд для разработки интерфейса

Настоящий сервер — Qt/C++, собирается docker'ом, и на рабочей машине его под
рукой обычно нет. А смотреть, как выглядит комната с людьми, демонстрацией и
чатом, нужно постоянно. Для этого есть `tools/mock-server.js` — раздача `dist`
плюс WebSocket, который отвечает на `join`, `ping`, `state`, `screen` и `chat`
и релеит бинарные кадры, как настоящий (вставляя `sender`). Медиа он не
разбирает вовсе.

```bash
node tools/build.js && node tools/mock-server.js
# http://127.0.0.1:9000/conference.html?room=DEV
```

Порт 9000 не случаен: страница по http всегда идёт на `ws://<хост>:9000`
(см. `wsUrl` в `meetup-common.js`). На другом порту получите работающую
вёрстку и мёртвый сокет.

Две служебные ручки — только у стенда, в продукт не попадают:

- `/dev-enter.html?name=…&room=…` кладёт имя в `sessionStorage` и уходит в
  комнату. Нужно, чтобы снимать конференцию headless-браузером: гейт
  «представьтесь» там руками не пройти.
- `?probe=1` дописывает к странице замер раскладки и кладёт результат в
  `<title>` — оттуда его достаёт `--dump-dom`.

Снять раскладку целиком:

```bash
msedge --headless=new --force-device-scale-factor=1 --window-size=520,900 \
       --screenshot=out.png "http://127.0.0.1:9000/dev-enter.html?name=Тест&room=DEV"
```

**Готча:** без `--force-device-scale-factor=1` headless рендерит страницу шире
окна (390 → 518 CSS px), и снимок выходит обрезанным справа — легко принять за
поломку вёрстки, которой нет. И само окно он не опускает ниже ~492 px, так что
проверить 320 px этим способом не получится.

## Страницы

| Файл | Назначение |
|---|---|
| `login.html` | Вход по аккаунту (`POST /api/auth/login`; живая сессия в куке ведёт на `home.html` автоматически) либо «Войти без аккаунта» → `anon_lobby.html`. Заголовок hero — случайная фраза из списка. |
| `register.html` | Регистрация: логин, отображаемое имя, пароль с повтором (`POST /api/auth/register`); после успеха — на `home.html` с сессией в куке. |
| `home.html` | Главная авторизованного пользователя (дизайн «Главная» из Claude Design): слева приветствие, под ним у низа — личная комната; справа «Другая встреча» (вход по коду, создание конференции) и «Недавние конференции» — история посещённых комнат из `localStorage` (`meetup.history`, пишет conference.html при входе; сервер историю не ведёт), клик — снова в комнату, можно удалить запись или очистить всё, под карточкой подпись про хранение только в браузере. На десктопе страница живёт без скролла (высота окна; длинная история крутится внутри карточки, на окнах ниже 760px включается компактный режим), на мобильном — обычная одноколоночная со скроллом. Смена имени через `PATCH /api/me`, аватарка — `POST/DELETE /api/me/avatar`, личная комната и её alias-ссылки — `/api/me/room*` (всё на сервере). Без сессии — редирект на `login.html`. |
| `anon_lobby.html` | Лобби анонимного пользователя: имя + код комнаты, либо «Создать трансляцию» (`POST /api/rooms`, код генерирует сервер). Заголовок hero — случайная фраза из списка. |
| `conference.html?room=<код>` | Конференция: плитки с видео и пагинацией, сцена под демонстрацию или закреплённого участника, чат с историей и картинками, ссылка-приглашение. При живой сессии аккаунта (`GET /api/me`) вход по ссылке сразу в эфир: имя из профиля, сервер по куке в WS-хендшейке выдаёт постоянный id (`2^31 + user id`); повторный вход с того же аккаунта вытесняет старое соединение (`session_replaced` — без авто-реконнекта). Аноним без имени видит гейт «Представьтесь». Док: микрофон, камера, общий звук, демонстрация (на телефоне её нет — `getDisplayMedia` там не работает ни в одном браузере), настройки, выход. Настройки — восемь разделов, см. ниже. |

## assets/

Общие ресурсы страниц (в браузере кэшируются, см. Cache-Control в
`HttpFileServer`):

- `react.js`, `react-dom.js`, `babel.js` — React 18.3.1 (dev-сборки) и
  @babel/standalone. Нужны только при работе с исходниками напрямую; в
  `dist` вместо них едут `react*.production.min.js`, а Babel не едет вовсе
  (см. «Сборка» выше);
- `meetup-ds.js` — дизайн-система (Card, Button, VideoTile, Icon…), глобал
  `window.MeetUpDesignSystem_2584b5`. Сборка из Claude Design, но четыре
  иконки (`volume`, `volume-off`, `maximize`, `minimize`) дописаны в `PATHS`
  руками — если бандл будут пересобирать, их надо вернуть. `ControlDock`
  оттуда конференция больше не берёт: в нём жёстко зашиты пять кнопок без
  «общего звука», и док собран на самой странице (`.dockbar`);
- `meetup-common.js` — помощники страниц: адрес WebSocket, fetch-обёртка
  `/api` (JSON-тело, кука сессии ходит сама), имя пользователя в
  sessionStorage, вызовы аккаунтов (`authLogin/authRegister/authMe/…`);
- `meetup-media.js` — медиадвижок конференции: бинарный протокол v2
  (`[type][flags][codec][ts]` + payload; сервер прозрачно вставляет sender),
  видео VideoEncoder (keyframe раз в 3 с и по запросу), звук AudioEncoder
  (Opus 48 кГц) с джиттер-буфером на AudioWorklet, фолбэк JPEG/PCM для
  браузеров без WebCodecs, E2E-слой AES-256-GCM (WebCrypto; PBKDF2 из фразы
  либо raw-ключ из `#k=`). Кодеки и звук демонстрации — ниже;
- `theme.css` — дизайн-токены (цвета/типографика/отступы/радиусы),
  тёмная тема по умолчанию, светлая через `[data-theme="light"]`;
- `fonts.css` + `fonts/*.woff2` — Manrope, Space Grotesk, Unbounded
  (self-hosted, без походов в Google Fonts).

## Отрисовка принятого кадра

Кадр рисуется формой `drawImage` из **девяти** аргументов: явно задаются и
источник (видимый прямоугольник кадра), и приёмник (весь холст). Короткая
форма `drawImage(frame, 0, 0, w, h)` задаёт только приёмник, а источником
берёт «всё изображение» — и что это такое для `VideoFrame`, реализации
трактуют по-разному. У HEVC закодированный размер выровнен по блокам и
крупнее видимой части, и картинка съезжала.

Строку кодека для HEVC пробуем начиная с `hev1`, а не `hvc1`, и это не
вкусовщина: `hvc1` означает «наборы параметров лежат вне потока и не
меняются», `hev1` — «могут приходить в самом потоке». Мы принимаем Annex B,
где SPS идёт с каждым опорным кадром, а ведущий может сменить разрешение
демонстрации посреди сеанса. Декодеру, настроенному как `hvc1`, менять
геометрию незачем — он остаётся с первым разрешением. Уровень объявляем с
запасом (6.2, до 8K): для приёма это потолок, и занизить его значит не суметь
показать 4K.

Что реально приходит по каждой полосе — кодек и размер кадра — видно в
разделе «Диагностика» («Приём · экран», «Приём · камеры»). Раньше там
показывался наш собственный кодек **отправки**, то есть во время чужой
демонстрации — неправда.

## Кодеки: отправлять узко, принимать широко

Отправляем H.264 — его понимают все. Принимаем всё, что вытянет браузер:
VP8, VP9, а также HEVC и AV1, если они у него есть. Это не симметрия ради
симметрии: десктопный клиент по умолчанию ведёт демонстрацию экрана в HEVC
(втрое экономнее H.264 по каналу), а камеру — в VP9, и без широкого приёма
браузер не показывал бы чужую демонстрацию до тех пор, пока не сработает
жалоба и отправитель не опустится на H.264.

Жалоба — это кадр `CODEC_UNSUPPORTED` (тип 9): его шлёт приёмник, наткнувшись
на кодек, которого не открывает, а сервер рассылает всем. Отправитель сверяет
кодек со своим (жалоба широковещательная и может быть не про него) и опускает
именно ту полосу, на которую пожаловались. Без этого ответа несовместимость
была бы молчаливой: у одного пусто, у другого всё хорошо, и никто не знает.

Строки кодеков для приёма проверяются через `VideoDecoder.isConfigSupported`
один раз за сессию и кэшируются — `configure()` на неподдержанном кодеке
падает не всегда синхронно, и без пробы приёмник крутился бы в цикле
«создать декодер — получить ошибку — создать заново».

Выбора кодека в интерфейсе нет и не планируется. В браузере эта ручка —
иллюзия управления: настоящий выбор делает WebCodecs, а каждый лишний кодек
в отправке — ещё один способ оказаться непонятым частью комнаты. VP8 остаётся
в отправке только как аварийный выход для браузера без H.264 (часть сборок
Firefox), VP9 из отправки убран.

## Битрейт под состояние сети

Голос, камера и экран едут через **один** WebSocket поверх TCP, поэтому
очередь в сокете задерживает всё сразу: пока не уйдёт опорный кадр экрана в
сотни килобайт, голос стоит за ним. Отсюда асимметрия — экран прижимаем
раньше и роняем первым, у камеры запас больше, звук не трогаем никогда:

| Полоса | Снижать битрейт с | Ронять кадры с |
|---|---|---|
| Экран | 200 КБ | 350 КБ |
| Камера | 400 КБ | 1,5 МБ |

Раньше здесь был один порог на обе полосы: очередь переросла полтора
мегабайта — кадр выброшен. Это обрыв, а не регулирование. Теперь множитель
битрейта падает на 20 % в секунду, пока очередь выше порога (не ниже
четверти пресета), и возвращается по 7 % в секунду, когда очередь пуста:
вниз реагируем быстро, вверх — втрое медленнее, иначе затор повторяется.
Битрейт меняется на живом энкодере (повторный `configure`), следующий кадр
делается опорным. Текущий множитель виден в `engine.stats()`
(`camRate`/`screenRate`).

## Звук демонстрации

Отдельная полоса (тип 8), а не подмешивание в голос: голос и фонограмма идут
от одного участника, но у Opus-декодера состояние потока — в один их класть
нельзя. Поэтому у каждого отправителя два независимых декодера и два плеера.

- **Отправка.** `getDisplayMedia({ video: true, audio: true })`. Галочку
  «Поделиться звуком» рисует сам браузер (Chrome и Edge умеют, Firefox и
  Safari — нет), и она же служит согласием: своей настройки нет, иначе человек
  разрешил бы, а мы всё равно не отправили. Стерео сводится в моно узлом Web
  Audio; Opus 64 кбит/с — вдвое против голосовых 32, это музыка и звук видео.
- **Приём.** Своя громкость у слушателя (`setScreenVolume`), а не у ведущего:
  иначе один человек решал бы за всю комнату. Ручка живёт на самой сцене и
  показывается, только пока звук реально идёт. По этой полосе не считают
  синхронизацию губ и не зажигают «говорит» — громкая музыка не значит, что
  человек говорит.

## Громкость: три независимых ручки

Общая громкость и «не слышу вас» одни на всех, но их не хватает: один
собеседник говорит шёпотом, другой кричит, а фонограмма демонстрации живёт
своей жизнью. Поэтому в графе Web Audio три уровня:

```
голос участника → узел участника → ┐
                                    ├→ общий узел → динамики
   звук демонстрации → узел экрана →┘
```

- **«Общий звук»** (кнопка в доке) глушит общий узел. Декодеры и джиттер-буферы
  при этом продолжают работать — иначе встали бы и картинка (её придерживают по
  часам звука), и подсветка «говорит». Не запоминается между входами: заходить
  в комнату оглохшим никто не хочет. Выключая звук, снимаем и микрофон, а
  возвращая — включаем обратно, но только если человек не распорядился им сам.
- **Личная громкость участника** — правая кнопка по плитке, на телефоне долгий
  тап (контекстного меню там нет, а ручка нужна одинаково). Помнится и для тех,
  кто молчит: узел создаётся при первом же его звуке.
- **Громкость демонстрации** — на сцене, см. выше.

К WebSocket клиент подключается в зависимости от схемы страницы:
по https — `wss://<host>/ws` (через nginx из [`../proxy`](../proxy/README.md)),
по http (локальная разработка) — напрямую `ws://<host>:9000`.

Протокол и HTTP API описаны в [`../docs/desktop-client-guide.md`](../docs/desktop-client-guide.md).

## Настройки: восемь разделов, одна разметка

Разделы и их порядок — как в десктопном клиенте (Звук · Видео · Демонстрация ·
Шифрование · Управление · Интерфейс · Диагностика · О программе): человек,
знакомый с одним клиентом, находит нужное во втором не глядя. Разметка одна на
обе раскладки, различается только CSS:

- на широком окне — рельс разделов слева и страница справа, прокрутка живёт
  внутри раздела (появление новых настроек не двигает вёрстку остальных);
- на телефоне — тот же список во весь экран и переход «список → раздел →
  назад». Крестик в этом режиме живёт в шапке списка: правая панель со своим
  крестиком спрятана, и без него из списка было бы не выйти.

Содержимое при этом другое, и намеренно. В браузере половина десктопных ручек —
фикция: кодек выбирает WebCodecs, разрешение и курсор демонстрации задаёт
системное окно доступа, глобальных клавиш не существует. **Заглушек «скоро» нет
ни одной**: если чего-то в вебе быть не может, раздел объясняет почему.

Что стоит знать про отдельные разделы:

- **Звук.** Шумоподавление, эхоподавление и автоусиление — браузерные (WebRTC
  APM). Они стоят до нашего захвата: в worklet приходит уже очищенный трек.
  Своего шумодава не тащим — это был бы WASM на пару мегабайт ради того, что
  уже есть и работает. Тумблеры применяются на живом треке через
  `applyConstraints`, микрофон не перезапускается.

  **Почему из трёх надёжно работает только автоусиление.** Эхоподавитель
  браузера вычитает из микрофона тот звук, который браузер сам же и играет —
  но опорный сигнал он берёт только с плеера WebRTC (`<audio>` с треком из
  `RTCPeerConnection`). Наши голоса играют через Web Audio (`AudioWorklet` →
  `GainNode` → `destination`), и для эхоподавителя этого звука не существует:
  ему нечего вычитать, и колонки честно возвращают собеседников в микрофон.
  Это давняя особенность Chromium (bug 687574), Firefox ведёт себя похоже, когда
  контекст звука живёт отдельно от графа микрофона. Известный обход — гнать
  микс через `MediaStreamAudioDestinationNode` и локальную петлю из двух
  `RTCPeerConnection` в `<audio>`; он не внедрён осознанно: это +50–100 мс
  задержки для всех, включая тех, кто в наушниках, и ещё один Opus-кодек по
  кругу. Шумоподавление же — штатное браузерное: ровный фон (вентилятор, гул)
  убирает, клавиатуру и стук — нет; RNNoise, как в приложении для Windows, стоил
  бы ещё столько же, сколько весь клиент. Сноска об этом висит прямо под
  тумблерами.
- **Управление.** Клавиши фиксированы (M · V · D · F · стрелки · Esc) и
  сравниваются по `e.code`, а не по введённому символу — иначе в русской
  раскладке «ь» вместо «m» ничего бы не работало. Сочетания с Ctrl/Alt/Cmd не
  перехватываем: это шорткаты браузера.
- **Диагностика.** Живые кбит/с и кадры в секунду считаются только пока раздел
  открыт. Скорости — за реальный промежуток с прошлого замера, а не «ровно за
  секунду»: интервал таймера плавает.
- **О программе** показывает, что этот браузер умеет кодировать и декодировать.
  Это не украшение: список объясняет, почему у одного участника чужая
  демонстрация идёт как есть, а у другого отправитель спускается на H.264.

## Чат

Устроен как в десктопном клиенте, и это осознанное копирование, а не совпадение:

- **лента прижата к низу** — разговор начинается снизу и растёт вверх. В CSS
  это не `justify-content: flex-end` (в прокручиваемом контейнере он обрезает
  верх, и до него не домотать), а `margin-top: auto` у ленты внутри;
- **шапка с именем и временем только у чужих сообщений** — своё имя человек
  знает, и строка над каждым своим пузырём съедала бы половину панели;
- **пузырь по ширине текста** (`display: inline-block` + `max-width: 82%`), а
  не во всю колонку: короткое «ага» не должно разъезжаться на всю панель;
- сообщения **не склеиваются в группы**: у каждого своя шапка, как в десктопе.

Единственное, что добавлено сверх десктопа, — прокрутка не отнимает место, где
человек читает: вниз уезжаем, только если и так были внизу (запас 80 px), иначе
показываем пилюлю «Новые сообщения». Десктоп делает то же самое, только
средствами `ListView` (`verticalLayoutDirection: BottomToTop`), где это
получается само.

Компонент `ChatMessage` из дизайн-системы не подошёл: он всегда рисует шапку,
в том числе у своих сообщений, и растягивает пузырь на всю ширину.

## Буфер приёма и отставание декодера

Декодер бывает медленнее потока — характерный случай — AV1 и HEVC на слабом
железе: кодируется быстро, разбирается медленно. Кадры копятся внутри
декодера, и картинка отстаёт ровно на длину этой очереди. Догнать её нельзя:
она наполняется быстрее, чем разгребается.

Отставание меряем **во времени, а не в кадрах**: «десять кадров» на 5 к/с —
это две секунды, а на 60 — одна шестая. Метка времени у нас сквозная (стенные
часы отправителя), поэтому разница между тем, что отдали декодеру, и тем, что
он выдал, — это ровно столько миллисекунд, на сколько картинка отстала.

- **Порог 900 мс.** Ниже 500 бывает всплеск от одного опорного кадра, который
  рассасывается сам; на секунде отставание уже мешает разговору. Ждать
  «нескольких секунд» поздно — к этому моменту человек успевает спросить
  «ты меня видишь?».
- **Второй сторож — очередь декодера больше 24 кадров**, на случай, когда
  меткам верить нельзя (часы отправителя прыгнули, старый клиент).
- **Сброс — это пересоздание декодера, а не `flush()`**: flush ДОЖИДАЕТСЯ
  разбора всей очереди, то есть делает ровно то, от чего мы уходим. После
  сброса ждём опорный кадр и просим его у отправителя (`KEYFRAME_REQ`).
- Сброс руками — кнопка на самой демонстрации и в «Диагностике». Чистит все
  полосы всех участников: человек жмёт её, когда отстало хоть что-то, и гадать,
  что именно, ему не нужно.
- Автоматический сброс показывает уведомление («отставало на 1,4 с — буфер
  сброшен»): молча «моргнувшая» картинка выглядит как сбой связи, а это была
  помощь.

Текущее отставание и число сбросов видны в «Диагностике».

## Выделение текста

Интерфейс — не документ. По умолчанию текст в нём не выделяется и не
показывает I-образный курсор: иначе любое перетаскивание по плиткам, доку и
настройкам подсвечивает подписи, а щелчок по имени участника выглядит так,
будто туда можно печатать. Выделение возвращено ровно там, где его хочется:
переписка, значения диагностики, поля ввода, название комнаты.

## Телефон

Веб-клиент один и тот же на компьютере и на телефоне — не «мобильная версия»,
а одна раскладка в двух размерах. Что сделано ради второго:

- **Микрофон и камера выключены на входе, разрешение спрашивается по кнопке.**
  Раньше комната встречала человека двумя системными окнами доступа сразу;
  теперь окно появляется в ответ на его собственное нажатие. Слышать других
  это не мешает: аудиограф поднимается отдельно (`ensureAudio`) — он нужен для
  воспроизведения, а не для захвата. Совпадает с умолчаниями десктопа.
- **Экран не гаснет** во время разговора (Screen Wake Lock). Браузер снимает
  блокировку, когда вкладка уходит в фон, поэтому берём её заново при
  возвращении.
- **Безопасные зоны** (`viewport-fit=cover` + `env(safe-area-inset-*)`): чёлка
  сверху и полоса жеста снизу больше не накрывают док, шапку, чат и настройки.
  Значения держим в переменных `--safe-*`: браузер без поддержки `env()` даёт
  пустоту, а не ноль, и повторять фолбэк в десятке мест не хочется.
- **Высота — `100dvh`**, а не `100%`. Адресная строка мобильного браузера то
  появляется, то уходит; обычные проценты меряются по большему размеру, и низ
  дока оказывался под ней.
- **Ландшафт.** При высоте меньше 480 px шапка, док и отступы сетки ужимаются:
  иначе на сцену не остаётся места.
- **В фоне не отправляем видео** (только на телефоне). Камера остаётся
  захваченной — иначе на возврате будет пауза и моргнёт индикатор, — но кадры
  в сеть не идут: батарею и трафик они едят, а никому не нужны. Звук
  продолжается, ради него в фон и уходят. На компьютере переключиться на другое
  окно посреди разговора — обычное дело, и пропадать из эфира там неправильно.
- **Демонстрации экрана на телефоне нет** и кнопки тоже: `getDisplayMedia` там
  не реализован ни в одном браузере.

## «Добавить на главный экран» (PWA)

`manifest.webmanifest` + `sw.js`. С ними страница ставится на телефон как
приложение: свой значок, запуск без адресной строки, ассеты не перекачиваются
при каждом заходе.

Service worker делает **ровно одно** — кэширует `/assets/`, и это осознанно:
сломанный service worker умеет запереть людей на старой версии так, что
обычным обновлением страницы это не чинится. Чем меньше он на себя берёт, тем
меньше ему ломать. Страницы, `/api/` и `/ws` он не трогает вовсе.

Кэшировать `/assets/` навсегда безопасно потому, что сборщик приписывает к
каждой ссылке `?v=<хэш содержимого>`: изменился файл — изменился адрес, и
старая запись просто перестаёт запрашиваться.

Регистрация требует защищённого контекста — по http (локальная разработка)
браузер её не даст, и это нормально. Серверу добавлен тип
`application/manifest+json` для `.webmanifest`: без него часть браузеров
манифест игнорирует.

## Режим разработчика

Тумблер в «О программе» — там же, где версия и сервер: это не настройка звука
или картинки, а признание «я разбираюсь, покажите служебное». Пока он выключен
(по умолчанию), нет раздела «Диагностика» и кнопки сброса буфера на
демонстрации.

Служебное именно **исчезает**, а не гаснет: приглушённый пункт человек всё
равно видит, читает и пытается понять, зачем он тут. Ровно так же сделано в
десктопном клиенте (`AV.devMode`), и раздел там помечен тем же признаком
`dev: true`. Текущий раздел настроек хранится **именем**, а не номером: номера
едут, когда «Диагностика» уходит из середины списка.
