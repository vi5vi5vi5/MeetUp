# MeetUp — сервер

Ретрансляционный сервер видеоконференций: принимает сжатые медиа-кадры от
участников и рассылает их остальным в той же комнате, **не заглядывая внутрь**.
Вдобавок сам раздаёт веб-клиент по HTTP и держит JSON API для аккаунтов и
комнат — поднимать отдельный веб-сервер или Python-хостинг для раздачи клиента
не нужно.

`C++20` · `Qt6 (Core · Network · WebSockets)` · `SQLite` · `CMake + Ninja`

> Это README — точка входа для того, кто хочет **собрать, запустить или
> дорабатывать** сервер. Философия проекта и «как поднять свой» простым языком
> для обычного пользователя будут в корневом README репозитория `MeetUp`.
>
> Не знаком с Qt? Смело листай сразу к разделу [**Qt за 5 минут**](#qt-за-5-минут) —
> он объясняет ровно те приёмы Qt, что встречаются в этом коде, и без него
> остальное читается тяжело.

## Что делает сервер

Один процесс совмещает три роли:

- **WebSocket-relay (SFU).** Сердце сервера. SFU (*Selective Forwarding Unit*)
  значит «пересылает, но не смешивает»: сервер получает поток каждого участника
  и копирует его остальным как есть. Он **не декодирует, не перекодирует и не
  микширует** видео и звук — поэтому лёгкий (несколько комнат тянет и слабый
  VPS) и добавляет минимум задержки. Плата за это — каждый участник отправляет
  свой поток серверу один раз, а сервер копирует его всем остальным — поэтому
  исходящий трафик сервера растёт примерно как N² от числа участников; для
  созвона друзей это не проблема.
- **HTTP-сервер статики** — отдаёт веб-клиент из `web/` (страницы, скрипты,
  шрифты). Встроен (`HttpFileServer`), внешний веб-сервер не требуется.
- **JSON API** (`/api/*`) — регистрация, вход, профиль, аватары, личные комнаты
  и ссылки-приглашения. Данные лежат в одном файле SQLite.

### Что уже умеет

- Комнаты: вход/выход, список участников, состояние микрофона и камеры
- Текстовый чат с временными метками и картинками (история отдаётся вошедшему)
- Демонстрация экрана (одна на комнату)
- Бинарный релей медиа; формат кадра серверу непрозрачен (клиенты шлют видео до
  720p — H.264/VP8/VP9 через WebCodecs, звук Opus, фолбэк JPEG/PCM)
- Сквозное шифрование по желанию участников: AES-256-GCM целиком на клиенте —
  сервер видит и хранит только шифротекст
- Аккаунты: регистрация, вход, сессии в HttpOnly-куке, отображаемое имя, аватары
- Личные комнаты с постоянным кодом-ссылкой и ссылки-приглашения (свой пароль,
  лимит использований, список допущенных логинов)
- Хранение в SQLite (WAL, один файл), скользящее продление сессий

## Как всё устроено

Слои зависят строго сверху вниз — верхний знает про нижний, но не наоборот:

```
main.cpp  →  network/  →  services/  →  interface/Abstract  →  sqlite | InMemory
                │             │                │
                └──► core/    └──► models/ ◄───┘
```

- **`network/`** говорит по сети (WebSocket и HTTP) и переводит запросы в вызовы
  сервисов. Про хранилище и бизнес-правила не знает.
- **`services/`** — правила: валидация, хеширование паролей, кто и куда вправе
  войти. Про сеть и про конкретную БД не знает.
- **`interface/`** — доступ к данным за абстрактным контрактом. Реализацию
  (`sqlite`) можно подменить (`InMemory`), не трогая сервисы.
- **`core/`** — то, что живёт в оперативной памяти во время звонка: сессии
  (`ClientSession`), комнаты (`ConferenceRoom`) и их реестр (`RoomRegistry`).
  Комнаты в БД не пишутся: код разовой комнаты — это и есть её «секрет».

**Кто чем владеет** (важно для Qt, см. ниже):

- `RoomRegistry` владеет комнатами (создаёт и удаляет).
- `ConferenceServer` владеет сессиями; `ClientSession` владеет своим сокетом.
- `ConferenceRoom` держит участников, но **не** владеет ими (просто список).
- Реестр комнат общий между `ConferenceServer` и `HttpApi`: HTTP API комнаты
  создаёт, WebSocket-relay подключает в них участников. Оба получают сырой
  указатель, а сам объект живёт в `main`.

### Путь одного медиа-кадра (горячий путь)

Это самый частый и самый оптимизированный маршрут в сервере — держи его в
голове, если будешь трогать релей:

```
QWebSocket (кадр от участника)
  → ClientSession::onBinaryMessageReceived   // сигнал "прилетели байты"
  → ConferenceServer::onBinary               // вставляет sender_id в заголовок
  → ConferenceRoom::broadcastBinary          // цикл по участникам комнаты
  → ClientSession::sendBinary → QWebSocket   // каждому, кроме отправителя
```

Сервер читает только первый байт кадра (тип сообщения) и подставляет
4-байтовый `sender_id` — остальное для него непрозрачные байты. Формат кадра
описан в `docs/` (бинарный протокол), но чтобы **пересылать** кадр, знать его
серверу не нужно. Один и тот же `QByteArray` рассылается всем без глубоких
копий (см. про copy-on-write в разделе про Qt).

## Сборка и запуск

### Локально — Windows (для разработки)

Пути к Qt и инструментам зашиты в начале `tools\build.ps1` — поправь, если Qt
лежит в другом месте.

```powershell
# Собрать: самодостаточный build\MeetUpServer.exe (нужные DLL кладутся рядом)
powershell -ExecutionPolicy Bypass -File tools\build.ps1

# Запустить
powershell -ExecutionPolicy Bypass -File tools\run.ps1
```

Порты по умолчанию:

| Назначение | Порт | Переопределить |
|---|---|---|
| WebSocket-relay | **9000** | `--ws-port N` |
| HTTP (веб-клиент + API) | **80** | `--http-port N` |

Другие аргументы: `--web-root <dir>` (где искать `index.html`), `--data-dir
<dir>` (куда класть базу и аватары). Полный список — `MeetUpServer.exe --help`.

> WebSocket по умолчанию на 9000, а не 8080: на машине автора порт 8080 держит
> Steam (remote-debugging на `127.0.0.1:8080`).

После запуска открой **http://localhost** и войди в одну комнату в двух вкладках
с разными именами — увидишь видео, список участников и общий чат.

### Docker (для настоящего сервера)

Для развёртывания «наружу» нужен HTTPS (камера в браузере работает только в
secure context), поэтому перед приложением ставится nginx-прокси, который
терминирует TLS. Минимальный запуск:

```bash
docker compose up -d --build
```

Затем открой **https://<IP-сервера>/**. Подробности про TLS, домены и
автопродление сертификатов Let's Encrypt — в [`proxy/README.md`](proxy/README.md);
пошаговую инструкцию для не-технаря позже добавим в корневой README проекта.

## Как добавить свою фичу

Два самых частых сценария — по шагам, чтобы не искать, куда что класть.

### Новый тип WebSocket-сообщения (например, «поднять руку»)

1. `network/ConferenceServer.cpp`, метод `onText` — добавь ветку
   `else if (type == QLatin1String("raise_hand")) handleRaiseHand(session, msg);`.
2. Напиши `handleRaiseHand(session, msg)`: возьми `session->room()`, проверь,
   что участник в комнате, и разошли остальным через `room->broadcastJson({...})`.
3. Опиши новый тип в `docs/` (§4, текстовый протокол), чтобы клиенты знали формат.

Состояние сессии (флаги вроде «рука поднята») удобно хранить в `ClientSession`
рядом с `micOn`/`camOn`.

### Новое поле или эндпоинт HTTP API (например, статус «не беспокоить»)

1. **Данные:** добавь поле в структуру в `models/`, колонку — в схему
   `interface/sqlite/SqliteDb.cpp` (`kSchema`) и в `bind`/чтение соответствующего
   репозитория (`Sqlite*.cpp`). Схема с `IF NOT EXISTS` переживает рестарт на
   уже существующей базе.
2. **Логика:** метод в сервисе (`services/`), где живут правила и валидация.
3. **Сеть:** обработчик в `network/HttpApi.cpp` и маршрут в `HttpApi::route`.
4. Опиши эндпоинт в `docs/` (§3, HTTP API).

Хранилище скрыто за интерфейсом (`interface/Abstract/`): правишь SQLite-реализацию,
а `InMemory` держи по образцу — на ней удобно гонять тесты без файла на диске.

## Qt за 5 минут

Весь сервер написан на Qt, но использует из него всего несколько идиом. Разберись
с этими пятью — и код станет обычным C++, а не «магией с макросами». Ссылки ведут
на живые примеры в этом проекте.

### 1. Событийный цикл: один поток, никаких блокировок

`main` заканчивается на `return app.exec();` (`main.cpp`) — это запуск
**событийного цикла**. Дальше сервер живёт в одном потоке и просто реагирует на
события: «пришёл байт в сокет», «сработал таймер», «новое подключение». Пока
обработчик (`onBinary`, `onText`, …) выполняется, ничего другого не происходит.

Отсюда два следствия:

- **Локи не нужны.** Комнаты и сессии трогает только этот поток — гонок нет,
  мьютексов нет. Это и делает релей простым и быстрым.
- **Нельзя блокировать надолго.** Тяжёлая операция в обработчике заморозит видео
  у всех. Поэтому дорогой расчёт хеша пароля вынесен в пул потоков, а результат
  возвращается обратно в главный поток (`AuthService.cpp`, `hashInPool` →
  `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`).

### 2. Сигналы и слоты: как события ходят по коду

Вместо колбэков и интерфейсов-наблюдателей Qt использует **сигналы** («что-то
случилось») и **слоты** (обработчики). Их соединяют через `connect`:

```cpp
// network/ConferenceServer.cpp
connect(session, &ClientSession::textReceived,   // сигнал источника
        this,    &ConferenceServer::onText);      // слот получателя
```

Источник «испускает» сигнал — `emit textReceived(this, text);`
(`ClientSession.cpp`), — и Qt вызывает все подключённые слоты. В одном потоке
это по сути обычный синхронный вызов функции, просто источник и получатель не
знают друг о друге напрямую. Так события сокета доходят до сервера, а сервер
остаётся отделённым от деталей `QWebSocket`.

### 3. Владение через parent: кто кого удалит

У каждого `QObject` может быть **родитель**. Удаляется родитель — автоматически
удаляются все его дети. Поэтому в коде почти нет ручного `delete`:

```cpp
// core/ClientSession.cpp — сокет становится ребёнком сессии
m_socket->setParent(this);            // умрёт вместе с сессией
// network/ConferenceServer.cpp — сессия становится ребёнком сервера
auto *session = new ClientSession(socket, this);
```

Когда участник отключается, сервер зовёт `session->deleteLater()` — это
«удалить, но не прямо сейчас, а когда событийный цикл освободится». Так безопасно
удалять объект изнутри его же обработчика сигнала. Правило простое: **создавай
`QObject` с родителем — и не думай об удалении**.

### 4. Copy-on-write: почему копировать `QByteArray` дёшево

`QString`, `QByteArray`, `QList`, `QJsonObject` — все с **неявным
разделением** (copy-on-write): при копировании они делят одни и те же данные и
копируют их по-настоящему только при попытке изменить. Скопировать `QByteArray`
на мегабайт — это скопировать указатель и увеличить счётчик ссылок.

Именно поэтому релей рассылает **один** кадр всем участникам без N копий:

```cpp
// core/ConferenceRoom.cpp — один QByteArray уходит всем
void ConferenceRoom::broadcastBinary(const QByteArray &data, ClientSession *except) const {
    for (ClientSession *s : m_sessions)
        if (s != except)
            s->sendBinary(data);      // данные общие, глубокой копии нет
}
```

На практике: не бойся возвращать эти типы по значению и передавать в функции;
для чистоты всё равно передавай по `const &`, чтобы не трогать даже счётчик.

### 5. `Q_OBJECT` и moc: откуда берётся «сгенерированный» код

Классы с сигналами и слотами обязаны наследовать `QObject` и содержать макрос
`Q_OBJECT` в начале объявления (`ClientSession.h`). При сборке Qt-шный
**moc** (meta-object compiler) читает такой заголовок и генерирует служебный
`.cpp` с реализацией сигналов и метаданными (те самые `moc_*.cpp`, что ты видел
в `build/`). Запускать его вручную не нужно — в `CMakeLists.txt` включён
`CMAKE_AUTOMOC`.

Что запомнить: **добавляешь сигнал/слот в класс → класс должен быть `QObject` с
`Q_OBJECT`**. Забыл `Q_OBJECT` — линковка упадёт с «undefined reference to
vtable» или «...::metaObject».

### Мини-словарь остального

| Встретишь в коде | Что это |
|---|---|
| `QString` / `QByteArray` | Текст (UTF-16) / сырые байты. JSON и медиа — это `QByteArray` |
| `QStringLiteral("x")`, `QByteArrayLiteral("x")` | Литералы, собранные на этапе компиляции (без аллокации в рантайме) |
| `QLatin1String("join")` | Дешёвое сравнение со строкой без создания `QString` |
| `QList` / `QHash` / `QSet` | Аналоги `std::vector` / `unordered_map` / `unordered_set` |
| `QJsonObject{{"type","join"}}` | Сборка JSON; сериализация — `QJsonDocument(obj).toJson(Compact)` |
| `std::optional<User>` | «Нашлось / не нашлось» — так репозитории отвечают на поиск |
| `QTimer` | Периодические задачи (чистка пустых комнат и протухших сессий) |
| `qInfo()` / `qWarning()` / `qCritical()` | Логирование в консоль |

Этого набора хватает, чтобы читать и дописывать любой файл сервера. За деталями —
[документация Qt](https://doc.qt.io/qt-6/): у каждого класса своя страница с
примерами.
